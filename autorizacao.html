Autorização de Parceiro

Processo de autenticação e autorização para aplicações parceiras (Portais de Parceiros / Multi-Tenant): da identificação do tenant à emissão do token de aplicação com escopos e canais, combinando federação de identidade (IDP) e Token Exchange no Axway API Gateway.

Visão geral

O parceiro se autentica no seu próprio Provedor de Identidade (IDP) externo. O BIAM não armazena credenciais: ele confia no IDP Subject (claim sub) e, a partir dele, resolve pessoa, usuário, tenant e os perfis/escopos por canal no banco transacional. No Axway, o token do IDP é então trocado (Token Exchange) pelo token definitivo da aplicação, já enriquecido com as claims resolvidas pela policy do BIAM.

Princípio. O IDP externo responde por quem é o usuário (autenticação). O BIAM responde por o que ele pode fazer (autorização): tenant, canais e escopos, além do kill-switch local (esta_bloqueado).

Fluxo E2E

1

Identificação de tenant

O frontend resolve o ambiente do parceiro por domínio/URL via GET /tenant e recebe a configuração Portais de Parceiros e o IDP associado.

↓
2

Autenticação SSO no IDP

A aplicação inicia o fluxo OIDC/OAuth 2.0 (ex.: AWS Cognito federando com Microsoft Entra ID). O usuário autentica e o IDP emite um token (com o claim sub).

↓
3

Token Exchange no Axway

A aplicação envia o token do IDP para POST /v1/authorization/exchange. O Axway conduz o exchange e aciona a policy do microsserviço, que valida a identidade contra o banco (IDP subject válido e e-mail existente).

↓
4

Emissão do token de aplicação

Com a autorização validada, o Axway emite o JWT definitivo, com tenant, canais e escopos agregados do usuário, usado nas chamadas às APIs protegidas.

Diagrama de sequência

Trocas entre os atores durante uma autorização bem-sucedida:

1Frontend → Axway: GET /tenant (por domínio)Resolve tenant, IDP e configuração Portais de Parceiros.
2Frontend → IDP (Cognito/Entra): Fluxo OIDC/OAuth 2.0Autenticação do usuário no provedor do parceiro.
3IDP → Frontend: subject_token (JWT com sub)
4Frontend → Axway: POST /v1/authorization/exchangegrant_type=token-exchange, subject_token, subject_token_type.
5Axway → BIAM: Valida sub + e-mail no bancoResolve pessoa/usuário/tenant e agrega scopes e canais; checa esta_bloqueado.
6BIAM → Frontend: Token de aplicação (JWT enriquecido)
7Frontend → APIs protegidas: Authorization: Bearer <token>
Detalhes de contrato dos endpoints em Endpoints REST; o modelo de dados e as queries de validação em Persistência & Acesso (OLTP).

Escopos e perfis por canal

O acesso é modelado por canal (ex.: whitelabel, developer) e perfil, sendo cada perfil associado a um scope único. Um mesmo usuário pode ter perfis em múltiplos canais.

CanalPerfilScope
whitelabelAdminbaas:portal-whitelabel:admin
whitelabelOperadorbaas:portal-whitelabel:operador
whitelabelConsumidorbaas:portal-whitelabel:consumer
developerAdminbaas:portal-developer:admin
developerOperadorbaas:portal-developer:developer
developerConsumidorbaas:portal-developer:consumer
Os escopos são resolvidos e agregados (STRING_AGG) na consulta de autorização — ver Consulta de autorização.

Token de aplicação

O token final é um JWT emitido pelo Axway, com as claims de identidade e autorização resolvidas pela policy do BIAM no banco. Exemplo ilustrativo do payload: 

{
  "iss": "https://api.openapi.baas.bank.com.br",
  "aud": "https://api.openapi.baas.bank.com.br",
  "sub": "admin@eufood.com",
  "idp_subject_id": "sub-idp-admin-eufood-123",
  "provedor": "COGNITO",
  "id_pessoa": "e0eebc99-9c0b-4ef8-bb6d-6bb9bd380a55",
  "tenant": "cacawshow",
  "canais": "whitelabel,developer",
  "scope": "baas:portal-whitelabel:admin baas:portal-developer:admin",
  "exp": 1788864000
}
Bloqueio. Se esta_bloqueado = TRUE na atribuição de perfil, o usuário é recusado independentemente do IDP externo ter autenticado com sucesso.

Referências normativas (RFC)

O fluxo se apoia em padrões abertos de identidade e autorização. Os links apontam para as especificações oficiais. As descrições resumem como cada padrão se aplica ao BIAM.

RFC 6749

The OAuth 2.0 Authorization Framework

Framework base de autorização (grant types, tokens de acesso).

No BIAM: fundamenta o fluxo OAuth entre aplicação e IDP e o vocabulário de scope/grant_type.

RFC 6750

OAuth 2.0 Bearer Token Usage

Uso de tokens do tipo Bearer em requisições HTTP.

No BIAM: o token de aplicação é enviado às APIs via cabeçalho Authorization: Bearer <token>.

RFC 7519

JSON Web Token (JWT)

Formato de token com claims assinadas.

No BIAM: tanto o subject_token do IDP quanto o token de aplicação são JWTs; as claims carregam tenant, canais e escopos.

RFC 8693

OAuth 2.0 Token Exchange

Troca de um token por outro (grant_type=token-exchange).

No BIAM: executado pelo Axway em /v1/authorization/exchange — troca o token do IDP pelo token de aplicação; o microsserviço apenas valida a identidade.

RFC 7636

Proof Key for Code Exchange (PKCE)

Proteção do Authorization Code para clientes públicos (SPAs).

No BIAM: recomendado no login OIDC do frontend com o IDP, mitigando interceptação do código.

OIDC Core

OpenID Connect Core 1.0

Camada de identidade sobre o OAuth 2.0 (claim sub, ID Token).

No BIAM: define o sub usado como idp_subject_id para localizar a pessoa no banco.
